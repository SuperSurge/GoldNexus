## 1. 背景与目标

### 1.1 原来的样子

`GoldNexusBackend` 原本是一个**单体（Monolith）应用**——一个金融借贷平台（金纽贷）的后端，所有代码都打包成**一个**可运行的程序。

技术栈：`Spring Boot 3.5.9 + Java 21 + MyBatis + Spring Security(JWT) + MySQL + WebSocket + Drools + DeepSeek AI`。

单体应用的特点：**所有功能（用户、贷款、文章、客服、AI…）都挤在同一个程序里**，共享同一个进程、同一个数据库连接池、同一份配置。

### 1.2 改造目标

把它拆成 **Spring Cloud 微服务分布式架构**，要求：

1. **功能完全不变**——原来能做什么，现在还能做什么；
2. **接口完全不变**——前端调用的 URL（`/goldnexus/**`）、请求参数、返回结果格式，一个字都不改；
3. **能正常运行**；
4. 产出一份**看得懂的说明文档**（就是你现在看的这份）。

> 换句话说：**对外看起来一模一样，对内变成了多个独立服务在协同工作。**

## 2. 先搞懂几个核心概念（很重要）

在动手之前，先用最通俗的比喻理解微服务的几个核心概念。

### 2.1 单体 vs 微服务

| | 单体（改造前） | 微服务（改造后） |
|---|---|---|
| 打比方 | 一家什么都做的**大超市** | 拆成**餐饮区、生鲜区、家电区**等多个独立小店 |
| 部署 | 一个程序，改一处要整体重启 | 每个服务独立打包、独立启动、独立升级 |
| 故障影响 | 一个模块挂了，整个程序可能都挂 | 一个服务挂了，其他服务还能用 |
| 数据 | 一个数据库 | 理想情况下每个服务一个库（本次为降低风险，暂共享一个库） |

微服务的核心思想是：**按业务领域把大应用拆成若干个小服务，每个服务只干自己那一摊事，服务之间通过网络通信协作。**

### 2.2 服务注册与发现（注册中心 Nacos）

问题来了：服务拆成好几个了，它们之间怎么知道对方在哪台机器、哪个端口？

这就要靠**注册中心**。它的作用类似**电话簿**：

1. 每个服务启动时，主动到注册中心**登记**自己的名字和地址（"我是 user-service，我在 8081 端口"）；
2. 其他服务或网关需要调用时，到注册中心**查询**（"user-service 在哪？"）；
3. 注册中心还会定期**体检**，发现某个服务挂了就把它从电话簿里划掉。

本项目用的注册中心是 **Nacos**（阿里开源，国内最流行），它同时支持"服务注册/发现"和"配置中心"两大功能（本次只用了注册发现）。

> 每个服务里那句 `spring.cloud.nacos.discovery.server-addr: 127.0.0.1:8848`，意思就是"我要到 8848 端口这个 Nacos 去登记"。

### 2.3 API 网关（Gateway）

拆成多个服务后，前端要调十几个不同的服务地址，很麻烦，而且每个服务的鉴权、跨域都要重复处理。

**网关（Gateway）**就是给所有服务加一个**统一大门**：

- 前端只跟网关打交道（还是原来的 `localhost:8080`）；
- 网关根据 URL 把请求**转发**到对应的后端服务；
- 网关统一处理**跨域（CORS）**、以后还可以统一做**限流、鉴权、日志**等。

本项目网关用的是 **Spring Cloud Gateway**（基于响应式 Netty，性能好）。

### 2.4 负载均衡（LoadBalancer）

网关配置里写的 `uri: lb://user-service`，这个 `lb://` 就是 **load balance（负载均衡）**。

意思是：网关不去记 user-service 具体在哪台机器，而是说"我要调用 **名为 user-service 的服务**"。然后由负载均衡器从注册中心里找到 user-service 的所有实例，选一个转发过去。这样即使 user-service 部署了 3 台机器，网关也能自动分摊流量。

### 2.5 配置中心（本次未启用，但要知道）

Nacos 还能当**配置中心**用：把配置文件放到 Nacos，所有服务从 Nacos 拉配置，改配置不用重启、一处修改处处生效。

本次为了**降低运行门槛、保证稳定**，配置仍放在每个服务自己的 `application.yml` 里，**暂未接入配置中心**（详见第 11 节）。

### 2.6 服务间调用（OpenFeign，本次未启用）

微服务之间互相调用，Spring Cloud 提供了 **OpenFeign**（写一个接口 + 注解，就能像调本地方法一样调远程服务）。

本次拆分后发现**各服务之间恰好不需要互相调用**（原因见 6.5 节），所以没有引入 Feign，避免引入分布式事务等复杂问题。

## 5. 各模块详细说明

### 5.1 父工程 `pom.xml`

- `<packaging>pom</packaging>`：声明这是个聚合父工程，自己不产代码，只负责"管孩子"。
- `<modules>`：列出 5 个子模块。
- `<dependencyManagement>`：通过 **BOM（物料清单）** 统一管理 `Spring Cloud 2025.0.0` 和 `Spring Cloud Alibaba 2025.0.0.0` 的版本。这样子模块引依赖时**不用写版本号**，避免版本冲突。
- 顺带**清理了原单体 pom 里的残留 Kotlin 配置**（原来没有 `.kt` 文件，纯属无用配置）。

### 5.2 `common`（公共模块）

**职责**：放那些"多个服务都要用、而且应该保持一致"的代码。

- `entity/`：全部 24 个实体类（`User`、`LoanProduct`、`Res` 统一返回体、`CurrentUser` 等）。因为多个服务都会用到这些实体，抽到一个公共模块，避免每个服务复制一份。
- `utils/JwtUtil`：生成和校验 JWT 的工具（**原样迁移**）。
- `utils/SecurityContextHelper`：从安全上下文取当前登录用户的工具（**原样迁移**）。
- `filter/JwtAuthenticationFilter`：JWT 鉴权过滤器（**原样迁移**）。
- `config/SecurityConfiguration`：Spring Security 安全配置（**做了小改造**，见 6.6）。
- `config/WebSocketConfiguration`：WebSocket 配置（原样保留；原项目实际没有用到 `@ServerEndpoint` 端点，但为保持行为不变，保留此配置）。

> common 是一个**库（jar）**，本身不能单独运行，它是被 3 个业务服务依赖的。

### 5.3 `gateway`（网关）

**职责**：唯一对外入口。负责：
- 把请求按 URL 路由到对应服务（`lb://服务名`）；
- 统一跨域配置（等价于原单体的 CORS 放行策略）。

**依赖**：`spring-cloud-starter-gateway-server-webflux`（网关本体）+ Nacos 发现 + LoadBalancer。

> 注意：网关**不依赖 common**。因为网关是响应式（WebFlux）技术栈，而 common 里的安全配置是 Servlet 技术栈，两者混用会冲突。所以网关是个完全独立的模块，只做转发、不做业务鉴权。

### 5.4 `user-service`（用户服务，8081）

**职责**：用户与管理员认证、用户信息、信用分、人脸识别。

| 层 | 内容 |
|---|---|
| controller | `UserController`（注册/登录/改密/实名）、`AdminLoginController`、`AdminUserController`、`CreditScoreController`、`FaceController`、`TestController` |
| service | `UserService`、`AdminLoginService`、`AdminUserService`、`CreditScoreService`、`FaceService` |
| mapper | `UserMapper`、`AdminLoginMapper`、`AdminUserMapper` |

**公开接口（无需登录）**：注册/登录共 4 个（与原单体一致，配置在 `security.permit-all`）。

### 5.5 `loan-service`（贷款服务，8082）

**职责**：贷款产品、申请、审核、还款计划、罚息、每日逾期扫描定时任务。

| 层 | 内容 |
|---|---|
| controller | `UserLoanController`、`UserRepayController`、`AdminLoanController`、`AdminProductController` |
| service | `UserLoanService`、`AdminLoanService`、`UserRepayService`、`UserPenaltyService`、`AdminProductService` |
| mapper | `UserLoanMapper`、`UserRepayMapper`、`UserPenaltyMapper`、`AdminLoanMapper`、`AdminProductMapper`，以及**精简版** `UserMapper`、`AdminUserMapper`（见 6.5） |

- 保留了 `@EnableScheduling`（`UserPenaltyService.check_overdue` 每天零点扫逾期算罚息）。
- 迁移保留了 Drools 依赖和 `loanRule.drl`（原单体本就未在代码里真正启用 Drools，仅保持一致）。

### 5.6 `content-service`（内容服务，8083）

**职责**：文章、AI 客服（DeepSeek）、人工客服、数据看板。

| 层 | 内容 |

| service | `UserArticleService`、`AdminArticleService`、`AiChatService`、`CustomerService`、`AdminDataService` |

## 6. 关键技术点逐一讲解

### 6.1 为什么接口 URL 能保持不变？

关键在**网关的路由表**。原来的 URL 是按 `/goldnexus/user/...`、`/goldnexus/admin/...` 组织的，而 `/goldnexus/user/` 下面**混杂了用户、贷款、文章、AI、客服等多个领域的接口**（这是历史原因）。

如果简单地"按 URL 前缀路由"（比如 `/goldnexus/user/**` 全部转到 user-service），就会把贷款、文章等接口也错误地转到 user-service。

所以本次采用**按精确路径逐条路由**：网关配置里，为每个服务**完整列出它承接的所有接口路径**。这样：

- `/goldnexus/user/login` → user-service
- `/goldnexus/user/products` → loan-service
- `/goldnexus/user/getArticles` → content-service

前端完全无感知，URL 一个都没变。

### 6.2 为什么 JWT 鉴权"下沉"到每个服务，而不是放在网关？

有两种做法：

- **方案 A（本次采用）**：网关**只转发不鉴权**，把 `Authorization` 请求头原样透传给后端，每个服务自己用 JWT 过滤器校验。
- **方案 B**：网关统一校验 JWT，校验通过后再转发，并在请求头里塞入用户信息，后端信任这些头。

选 A 的原因：

1. **改动最小、行为最一致**：原单体的 JWT 过滤器直接搬进 common，每个服务复用，逻辑一字不差；
2. **更安全**：方案 B 里后端要"信任网关头"，一旦有人绕过网关直接访问服务，可能伪造头信息；方案 A 每个服务自己校验，更稳健；
3. **网关保持轻量**：网关只干"转发"这一件事，职责清晰。

**代价**：`jwt.secret` 必须在每个服务配置里保持一致（本项目都是 `nihao123321`）。这正是"JWT 是无状态令牌"的体现——只要密钥一致，任何服务都能校验同一个 token。

### 6.3 共享数据库（一个 `goldnexus` 库）

**理想**的微服务是"**一服务一数据库**"（用户库、贷款库、文章库各自独立）。

但本次选择了**共享一个 MySQL 库**，原因是：

1. 原单体的多个 Mapper 之间存在**跨表查询**（例如管理员"按姓名查贷款申请"要先查 `user` 表拿到 id，再查 `loan_application` 表）。拆库意味着这些 SQL 要重构成跨服务调用，改动巨大、极易出错。
2. 拆库会引入**分布式事务**（一个业务操作跨多个库，要保证一致性），这对入门来说过于复杂。
3. 目标是"功能不变、能正常运行"，共享库是风险最低、最稳妥的过渡方案。

> 共享库是微服务里公认的"反模式"，但在**单体拆分的第一阶段**，它是非常务实的选择。本文第 11 节会说明如何一步步演进到"一服务一库"。

### 6.4 loan-service 为什么有自己的 `UserMapper`？

loan-service 里有两个"精简版" Mapper：`UserMapper`（只有 `selectUserById`）和 `AdminUserMapper`（只有 `selectUserByName`）。

原因：贷款业务的逻辑需要读 `user` 表（比如申请贷款时要查当前用户信息）。在共享库的前提下，loan-service **直接访问同一张 `user` 表**即可，所以它声明了自己需要的、只读的 Mapper 方法，**而不是**去调用 user-service。

这体现了共享库模式的一个特点：**数据层可以跨服务直接访问，业务层（service）则各自独立。**

### 6.5 为什么本次不需要 Feign（服务间调用）？

原单体里唯一的"服务依赖服务"是 `AdminLoanService` 依赖 `UserLoanService`（审核通过后调用 `generateRepayment` 生成还款计划）。这两个类**都属于贷款领域**，拆分时把它们放在**同一个 loan-service** 里，依赖关系保持不变，自然就不需要跨服务调用。

其余跨领域的数据读取，都靠"共享库 + 各服务自带 Mapper"解决了。

因此本次**没有引入 Feign**。若将来要做真正的跨服务调用（比如内容服务要查用户昵称），再引入 OpenFeign 即可（见 11.3）。

### 6.6 SecurityConfiguration 白名单"可配置化"

原来单体的 `SecurityConfiguration` 里，公开接口（登录/注册）是**硬编码**写死的 4 个路径。

拆成多个服务后，**每个服务的公开接口不一样**（user-service 有登录注册，loan-service、content-service 完全没有公开接口）。于是做了个小改造：

- 把公开路径改成从配置读取：`@Value("${security.permit-all:}")`；
- user-service 在 `application.yml` 里配了那 4 个路径；
- loan-service、content-service 不配，默认全部需要登录。

这样一份安全配置代码，三个服务各取所需。

### 6.7 为什么要清理原 pom 里的 Kotlin 和编译插件配置？

原单体 `pom.xml` 里有 `kotlin-maven-plugin`、`kotlin-stdlib`，还手动改写了 `maven-compiler-plugin` 的执行阶段。但整个项目**没有任何 `.kt` 文件**，这些配置是早期遗留的无用配置，甚至会干扰 Java 编译（比如把 `jvmTarget` 设成 1.8，与 Java 21 矛盾）。

拆模块时，每个模块都用了**标准、干净**的 Spring Boot 构建配置，顺带把这些残留清理掉了。功能不受任何影响。

## 8. 如何运行

### 8.0 前置条件

- **JDK 21**（本机路径 `/opt/homebrew/opt/openjdk@21`，若你的 Maven 默认用了别的 JDK，请设置 `JAVA_HOME`）
- **Maven 3.9+**
- **MySQL** 已启动（库 `goldnexus` 已存在，账号密码见各服务 `application.yml`）
- **Nacos 服务端**（下面第 1 步下载启动）

### 8.1 启动 Nacos（注册中心）

```bash
# 1) 下载 Nacos 2.5.4（约 150MB）
curl -L -o nacos-server-2.5.4.zip \
  https://github.com/alibaba/nacos/releases/download/2.5.4/nacos-server-2.5.4.zip

# 2) 解压
unzip nacos-server-2.5.4.zip

# 3) 以单机模式启动（standalone）
cd nacos
export JAVA_HOME=/opt/homebrew/opt/openjdk@21   # 换成你自己的 JDK 21 路径
sh bin/startup.sh -m standalone
```

启动成功后，浏览器访问 **http://localhost:8848/nacos** 能打开控制台即可（2.5.x 单机模式默认无需登录）。

### 8.2 构建整个工程

在项目根目录 `GoldNexusBackend/` 下执行：

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@21
mvn clean install -DskipTests
```

> 这会按顺序编译 common → gateway → 三个服务，并把 common 安装到本地 Maven 仓库。

### 8.3 依次启动 4 个程序（建议开 4 个终端窗口）

```bash
# 终端 1：启动用户服务（8081）
cd user-service && java -jar target/user-service-0.0.1-SNAPSHOT.jar

# 终端 2：启动贷款服务（8082）
cd loan-service && java -jar target/loan-service-0.0.1-SNAPSHOT.jar

# 终端 3：启动内容服务（8083）
cd content-service && java -jar target/content-service-0.0.1-SNAPSHOT.jar

# 终端 4：启动网关（8080，最后启动）
cd gateway && java -jar target/gateway-0.0.1-SNAPSHOT.jar
```

也可以用 `mvn spring-boot:run` 代替 `java -jar`（效果一样）。

### 8.4 停止

- 各服务：在对应终端按 `Ctrl+C`。
- Nacos：`cd nacos && sh bin/shutdown.sh`。

## 10. 常见问题排查

| 现象 | 可能原因 | 解决 |
|---|---|---|
| 服务启动报 `Connection refused` 到 8848 | Nacos 没启动 | 先启动 Nacos（8.1） |
| 网关返回 404 | 该路径没在网关路由表里 | 检查 `gateway/application.yml` 的 `routes` 是否包含该路径 |
| 网关返回 503/无法访问服务 | 服务没注册成功 或 IP 不通 | 看 Nacos 控制台服务是否在线；确认服务已启动 |
| 前端跨域报错 | 网关跨域配置问题 | 检查 `globalcors` 配置 |
| 带 token 却返回 401 | `jwt.secret` 不一致 或 token 过期 | 确认所有服务 `jwt.secret` 相同；重新登录拿新 token |
| 数据库报错 | MySQL 没启动 / 账号密码不对 | 核对 `application.yml` 里的数据源配置 |
| `mvn` 用了 JDK 25 报错 | `JAVA_HOME` 指向了高版本 | 显式 `export JAVA_HOME=<JDK21 路径>` |

## 11. 进一步演进建议

本次改造是"微服务第一步"，把单体成功拆开并跑通。以下是后续可以继续深入的方向（按建议顺序）：

### 11.1 接入 Nacos 配置中心

把各服务的 `application.yml` 里公共的部分（如数据源、jwt 密钥）放到 Nacos 配置中心，实现**改配置不重启、多服务一处生效**。

### 11.2 数据库拆分（一服务一库）

逐步把共享库拆成独立库：
1. 先按表归属拆分：`user` 相关表 → user 库；`loan_*` → loan 库；`article/ai_chat/customer_service` → content 库；
2. 跨服务的数据读取从"直接查表"改为"OpenFeign 调用对方接口"；
3. 引入分布式事务方案（如 Seata）解决跨库一致性。

### 11.3 引入 OpenFeign 做服务间调用

当出现真正的跨服务调用需求时，引入 `spring-cloud-starter-openfeign`，定义 `@FeignClient` 接口即可。

### 11.4 引入熔断与限流（Sentinel）

用 Sentinel 保护服务，防止某个服务故障导致雪崩，实现流量控制、熔断降级。

### 11.5 网关统一鉴权

若希望网关统一校验 JWT（方案 B），可在网关加一个全局过滤器，校验通过后把用户信息写入转发头，后端改为信任这些头（需配合网络安全策略防止绕过网关直连）。

### 11.6 链路追踪与监控

引入 Spring Boot Actuator + Micrometer + 链路追踪（如 SkyWalking），观测每个请求在多个服务间的流转与耗时。
